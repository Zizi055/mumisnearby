# Сверка документации `frontend-b2b.md` с тем, что отдаёт сервер

Дата: 16 октября 2026. Сервер: rodnoygolos.ru и rodnyegolosa.ru — у них
один бэкенд, `127.0.0.1:8000`.

Откуда данные. Список маршрутов сервера я взяла из его собственной схемы:
`curl http://127.0.0.1:8000/openapi.json` прямо на машине (снаружи этот
адрес не проксируется, поэтому только по ssh). Список вызовов фронта —
поиском по `lk/src/api`. Список из документации — выборкой строк вида
`GET /путь` из `frontend-b2b.md`. Ничего не додумано, всё три списка
можно собрать заново теми же командами.

---

## Коротко

Корпоративного модуля на сервере нет вообще. Из 26 адресов, описанных в
`frontend-b2b.md`, работают 6 — и все шесть относятся к обычному
кабинету, который существовал до корпоративной версии. Ни одного адреса
с `/companies` или `/admin/companies` в схеме сервера нет.

Поэтому логин и пароль «для входа как компания» сейчас отправить некуда:
адрес `POST /companies/auth/login`, на который фронт их отправляет,
отвечает 404.

## 4. Неточности в самой документации

**Один и тот же адрес назван по-разному.** В одном месте
`GET /admin/companies/{company_id}/slots`, в другом
`GET /admin/companies/{id}/slots`. Это мелочь, но при генерации клиента
по документу получаются два разных метода.

**Не сказано, что роли не наследуются.** Токен суперадминистратора на
`/admin/*` даёт 401, туда нужен токен обычного администратора. В коде
фронта это записано как проверенный на сервере факт, в документе —
ни слова. Человек читает документ, берёт суперадминский токен и упирается
в 401 без объяснений.

**Не описано, что бывает после истечения договора.** В коде заложено,
что компания ещё может войти и смотреть данные, но добавление
сотрудников и смена тарифов отвечают 403. В документе этого нет.

## 5. Отдельная проблема: `/admin/` отдаёт HTML вместо JSON

Запрос `GET /admin/companies?skip=0&limit=100` вернул не JSON с ошибкой,
а целую HTML-страницу: внутри ссылки на `/admin/statics/css/tabler.min.css`
и `<title>Admin</title>`. То есть на `/admin` смонтирована ещё и серверная
админ-панель, и она перехватывает все адреса `/admin/*`, которые не
описаны в FastAPI, отдавая свою страницу «404 Not Found».

Чем это плохо для любого клиента, не только нашего: вместо
`{"detail": "..."}` приходит разметка, разобрать её нельзя, и в интерфейс
вываливается простыня тегов. У нас это уже случилось — на экране выбора
компании вместо сообщения была страница с тегами.

Два варианта, оба на стороне бэкенда: либо отдать корпоративному разделу
собственный префикс (`/api/admin/companies`), либо заставить монтированную
админку отвечать JSON на запросы с `Accept: application/json`. Первый
надёжнее.

На стороне фронта я уже подстелила соломки: если в ответе приходит HTML,
показывается текст «Этого раздела нет в API сервера», а не разметка.

## 6. Чего не хватает для экранов, которые уже нарисованы

Это не ошибки документации, а недостающие данные. Экраны сотрудника и
компании готовы, но заполнять их нечем:

- **`company_id` и название компании в `GET /auth/who_am_i`.** Сотрудник
  корпоративной версии должен видеть, от какой компании у него доступ.
  Сейчас в ответе этого нет.
- **Контакт администратора компании.** Сотруднику некуда обратиться по
  вопросам доступа.
- **Дата подключения сотрудника.** Её нет ни в одном ответе.

## 7. Что я предлагаю спросить у бэкенда

1. На какой адрес отправлять логин и пароль, которые выдали «для входа
   как компания»? В схеме сервера подходящего адреса нет.
2. Когда планируется выкатить корпоративный модуль — списки из разделов 2
   и 3 этого документа?
3. Останется ли раздел компаний под префиксом `/admin/`, учитывая, что там
   уже живёт серверная админка (раздел 5)?
4. Будут ли добавлены поля из раздела 6?

Фронт по всем перечисленным адресам уже написан и собран. Как только
бэкенд их отдаст, ничего переделывать не придётся — кроме случая, если
поменяется префикс `/admin/companies`: тогда правка в одном файле,
`lk/src/api/companySession.js`.
