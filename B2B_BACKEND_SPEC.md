# B2B-версия: что нужно от бэкенда

Документ для бэкенд-разработчика. Описывает всё, чего сейчас нет в API и
без чего корпоративный личный кабинет работать не сможет.

Фронтенд живёт в том же репозитории и собирается как вторая редакция
(`VITE_EDITION=b2b`) того же приложения. База данных, авторизация
пользователей, голоса, библиотека и генерация — **общие с B2C**, их
переделывать не нужно. Новое — только корпоративный слой поверх.

Домен B2B: `rodnoygolos.ru`, тот же сервер, отдельный блок nginx.

---

## 1. Сущности

### Company

Корпоративный клиент.

| поле | тип | описание |
|---|---|---|
| `id` | int | он же `COMPANY_ID` в промокоде |
| `name` | str | название компании |
| `inn` | str \| null | для счёта |
| `contact_name` | str | ФИО HR-администратора |
| `contact_email` | str | он же логин HR |
| `contact_phone` | str \| null | |
| `plan_id` | int | тариф: **3** Сказочник, **4** Хранитель, **5** Волшебник — те же ID, что уже в таблице тарифов, новых строк не нужно |
| `seats_total` | int | оплачено мест |
| `seats_used` | int | активировано сотрудниками (считается, не хранится) |
| `billing_period` | enum | `month` \| `year` |
| `status` | enum | `trial` \| `active` \| `expired` \| `cancelled` |
| `started_at` | datetime | |
| `expires_at` | datetime | |

**Цена считается за одного сотрудника в год.** Актуальные значения:
Сказочник 24 000, Хранитель 31 200, Волшебник 59 900. Итог к оплате —
`цена тарифа × seats_total`. Если решим вводить скидки от объёма, нужна
таблица порогов; пока порогов нет.

### CompanyAdmin (HR)

Отдельная учётка, не пользователь ЛК и не админ поддержки. Третья роль.

| поле | тип |
|---|---|
| `id` | int |
| `company_id` | int |
| `email` | str, уникальный |
| `password_hash` | str |
| `full_name` | str |
| `created_at` | datetime |

Токен подписывается своим ключом и несёт `role: hr`, по аналогии с тем,
как уже сделано для `admin` / `super_admin`.

### PromoCode

| поле | тип | описание |
|---|---|---|
| `code` | str, уникальный | см. формат ниже |
| `company_id` | int | |
| `plan_id` | int | тариф, который выдаётся при активации |
| `expires_at` | datetime | срок действия |
| `max_activations` | int | по умолчанию 1 |
| `activations_count` | int | |
| `status` | enum | `active` \| `used` \| `expired` \| `deactivated` |
| `created_at` | datetime | |

**Формат кода.** В ТЗ указано `RODN-GOLOS-{COMPANY_ID}-{UUID}`. Полный
UUID — 36 символов, такой код сотрудник руками не введёт и по QR-коду
глазами не сверит. Предлагаю:

```
RODN-GOLOS-{COMPANY_ID}-{8 символов}
пример: RODN-GOLOS-17-K4P9TXM2
```

Алфавит — 32 символа без визуально похожих (`0 O 1 I l` исключены):
`ABCDEFGHJKLMNPQRSTUVWXYZ23456789`. Это 32⁸ ≈ 1,1 × 10¹² комбинаций на
компанию — коллизий не будет, а ввести можно вручную. Регистр при
проверке игнорируем, дефисы при вводе не обязательны.

**QR-коды генерирует фронтенд** (библиотекой в браузере). От бэкенда
нужен только сам код — отдельный эндпоинт для картинки не требуется.

### Связь сотрудника с компанией

К существующей таблице пользователей добавить:

| поле | тип | описание |
|---|---|---|
| `company_id` | int \| null | `null` — обычный B2C-пользователь |
| `activated_promo_code` | str \| null | каким кодом вошёл |

## 2. Эндпоинты

### 2.1. Регистрация компании и вход HR

```
POST /b2b/companies/register
     { name, inn?, contact_name, contact_email, contact_phone?,
       plan_id, seats_total, billing_period, password }
  → 201 { company: Company, access_token }
     409 — email уже занят
```

Создаёт компанию в статусе `trial` (3 дня, как обещано в гарантиях) и
учётку HR. Оплата — отдельным шагом через существующую ЮKassa.

```
POST /auth/hr/login          (form-urlencoded: username=email, password)
  → 200 { access_token, token_type }

GET  /auth/hr/me             → 200 CompanyAdmin
GET  /b2b/company            → 200 Company   (компания текущего HR)
PATCH /b2b/company           { name?, inn?, contact_* }  → 200 Company
```

### 2.2. Промокоды

```
POST /b2b/promocodes/batch
     { count, plan_id, expires_at, max_activations? }
  → 201 { items: PromoCode[] }
     400 — count превышает свободные места (seats_total − seats_used − уже выданные активные)
```

Генерация пачкой: HR указывает количество, тариф и срок. Выдать кодов
больше, чем оплачено мест, нельзя — иначе сотрудник активирует код и
получит отказ, что хуже, чем не получить код.

```
GET   /b2b/promocodes?status=&page=&page_size=
  → 200 { items: PromoCode[], total, page, page_size }
        status: active | used | expired | deactivated (без параметра — все)

PATCH /b2b/promocodes/{code}/deactivate   → 200 PromoCode
```

### 2.3. Активация сотрудником

```
POST /promo/validate   { code }        — без авторизации
  → 200 { valid: true, company_name, plan_id, plan_name }
     200 { valid: false, reason: "expired" | "used" | "deactivated" | "not_found" }
```

Проверка **до** регистрации: сотрудник вводит код и сразу видит, в какую
компанию и на какой тариф он попадёт. Отвечать 404 нельзя — фронту нужна
причина отказа, чтобы показать человеку осмысленный текст.

```
POST /promo/activate   { code, email, username, password, phone_number? }
  → 201 { access_token, company_name, plan_name }
     400 { detail: "expired" | "used" | "deactivated" | "no_seats" }
```

Одной операцией: создаёт пользователя, привязывает к компании, включает
подписку по тарифу кода, увеличивает `activations_count`. Отдельной
оплаты нет — доступ оплачен компанией.

Если пользователь с таким email уже есть (был B2C-клиентом), код должен
просто привязать его к компании, а не создавать второго:

```
POST /promo/attach     { code }        — с токеном существующего пользователя
  → 200 { company_name, plan_name }
```

### 2.4. Сотрудники и статистика для HR

```
GET /b2b/employees?page=&page_size=&q=
  → 200 { items: [{ id, username, email, activated_at,
                    voice_ready: bool, generations_count,
                    last_active_at }], total, page, page_size }

GET /b2b/stats?from=&to=
  → 200 { seats_total, seats_used, seats_free,
          promo_issued, promo_activated, promo_expired,
          voices_recorded, generations_count,
          active_employees_30d,
          expires_at }
```

Этого достаточно и для дашборда HR, и для обещанной в ТЗ «ежемесячной
аналитики по использованию льготы».

Персональные данные детей, тексты и записи голосов в статистику **не
попадают** — HR видит только факт активности. Это важно и для 152-ФЗ, и
для доверия сотрудников: иначе корпоративную льготу никто не включит.

### 2.5. Заявки с лендинга

```
POST /b2b/leads
     { company_name, contact_name, email, phone?,
       employees_count?, type: "demo" | "pricing" }
  → 201 { id }

GET  /b2b/leads?page=      — для админки поддержки
  → 200 { items, total, page, page_size }
```

На B2B-лендинге две формы: «Запросить демо для HR-команды» и «Рассчитать
стоимость для вашей численности». Это один эндпоинт с разным `type`.

Попутно: таких эндпоинтов нет и для B2C — форма на главной
`rodnyegolosa.ru` сейчас отправляет заявки в никуда, страница «Заявки» в
админке пустая. Стоит сделать сразу для обоих.

## 3. Чего не хватает в ЛК сотрудника

ТЗ требует этого от кабинета сотрудника, а эндпоинтов нет.

```
POST /generations/{id}/played          → 204
GET  /listening-history?page=
  → 200 { items: [{ generation_id, content_type, content_id,
                    played_at }], total, page, page_size }
```

«История прослушиваний» — события воспроизведения сейчас вообще не
пишутся, показывать нечего.

```
GET   /profile/notifications
PATCH /profile/notifications  { generation_ready, ticket_reply, system }
  → 200 { ... }
```

Настройки уведомлений сейчас только клиентские (звук в localStorage), на
другом устройстве не применяются.

```
PATCH /voices/{voice_id}   { name?, description? }   → 200
```

«Перезапись голосовой модели» сейчас возможна только как «удалить и
создать заново» — переименовать нельзя.

**«Скачать для офлайн-доступа»** отдельного эндпоинта не требует:
подойдёт существующий `GET /generations/{id}/audio`. Но важно понимать
ограничение — скачать можно только **уже озвученный** материал, и ссылка
живёт час. На карточке неозвученной сказки кнопка «Скачать» бессмысленна.

## 4. Исправления в текущем API

Не связано с B2B, но ломается уже сейчас.

**`FamilyStoriesListResponse` и `StoriesListResponse`** — поля
`description`, `category`, `age` объявлены обязательными и non-nullable,
хотя в БД nullable. Одна строка с `NULL` роняет весь список в 500. Так
уже произошло с семейными историями: раздел не открывался, пока в базе не
заменили `NULL` на пустые строки. У `FairyTaleListResponse` те же поля
`Optional` — привести к одному виду.

**`BillingPeriod`** — в enum осталось значение `free`, хотя бэкенд его
отвергает с 400. Убрать из схемы, чтобы не вводить в заблуждение.

**`prometheus-fastapi-instrumentator`** — версия не закреплена в
`requirements.txt`. Новый релиз убрал параметр `should_group_status_codes`,
и `skazki_app` дважды падал в crash-loop с `TypeError` в `main.py:79` —
сайт лежал целиком. Закрепить версии всех зависимостей.

**`/api/content/stories`** — в описании эндпоинта написано «Возвращает
список семейных историй», а возвращает рассказы. Косметика, но путает.

## 5. Порядок работ

1. Исправления из раздела 4 — они чинят уже существующие поломки.
2. `Company`, `CompanyAdmin`, авторизация HR (раздел 2.1).
3. Промокоды: генерация, список, деактивация (2.2).
4. Активация сотрудником (2.3) — после этого фронт можно собирать целиком.
5. Статистика и сотрудники (2.4).
6. Заявки (2.5) — сразу для B2B и B2C.
7. Доработки ЛК сотрудника (раздел 3).

Фронтенд готов работать по этой схеме без дальнейших согласований. Если
какое-то имя поля или путь удобнее сделать иначе — скажи до реализации,
поправлю у себя; переделывать после выката дороже.
